## 2. สาขา A (ทางเลือกอนาคต): Idempotency-Key-At-Session

**แนวคิด:** ผูก `idempotency-key` ไว้ที่ระดับเซสชัน ใช้คีย์ `task:op:attempt` ผูกกับ `session id` แล้วตรวจซ้ำก่อนสร้างงานจริง

**โฟลว์:**

1. สร้างคีย์ `task:op:attempt` จาก `session id` ทุกครั้งก่อนสร้างโอเปอเรชัน
2. ตรวจซ้ำว่ามีคีย์นี้แล้วหรือไม่ ถ้ามีให้คืนค่าของเดิม ไม่สร้างใหม่
3. ถ้ายังไม่มีจึงสร้าง แล้วบันทึกคีย์ผูกกับ `session id` ทันที

**สถานะ:** ไม่ทำรอบนี้ เก็บเป็นดีไซน์อนาคตเมื่อมี session API จริงเท่านั้น

## 3. สาขา B (สาระหลัก): ถ้อยคำ Best-Effort + เสนอแก้ design.md

**หลักการ:** ยอมรับข้อจำกัดว่าไม่มี API ค้นเซสชันจริง ทำได้แค่เท่าที่ไฟล์บอกได้ ไม่รับประกันความครบถ้วน

**ถ้อยคำ best-effort ที่เสนอ:**

> `discover` เป็นแบบเบสต์-เอฟเฟิร์ตจากหลักฐานไฟล์โลคัลเท่านั้น ค้นเท่าที่ไฟล์บอกได้ ไม่รับประกันว่าครบหรือตรงกับสถานะจริง

**เสนอแก้ `design.md`:**

1. §26.34 เติม `file-based evidence only` ที่แถว `discover` ให้ชัดว่าไม่ใช่การค้นจริง
2. เพิ่มข้อ 7 ว่า "ค้นเท่าที่ไฟล์บอกได้ ไม่รับประกัน" เพื่อกันความเข้าใจผิดของผู้เรียกใช้
3. กำหนดฟอลแบ็กตามลำดับ `checkpoint → events → state` เมื่อหลักฐานชั้นบนไม่มีให้ตกไปชั้นถัดไป

**ลำดับฟอลแบ็ก:**

1. `checkpoint` — ใช้ก่อนถ้ามี เพราะตรงที่สุด
2. `events` — ใช้เมื่อไม่มี `checkpoint` ประกอบภาพจากอีเวนต์เท่าที่มี
3. `state` — ใช้สุดท้ายเป็นภาพคงเหลือเท่าที่ไฟล์บอกได้

## 4. เกณฑ์ผ่าน + ความเสี่ยงสาขา A/B

**เกณฑ์ผ่าน:**

- สาขา B: ถ้อยคำ §26.34 + ข้อ 7 ตรงตามที่เสนอ ฟอลแบ็กเรียง `checkpoint → events → state` ถูกต้อง ไม่เคลมว่าเป็นการค้นจริง
- สาขา A: มีแผนคีย์ `task:op:attempt` ผูก `session id` พร้อมขั้นตอนตรวจซ้ำก่อนสร้าง (ยังไม่ต้องอิมพลีเมนต์รอบนี้)
- ไฟล์นี้ไฟล์เดียว ไม่แตะไฟล์อื่น ไม่คอมมิต

**ความเสี่ยง:**

| สาขา | ความเสี่ยง |
|---|---|
| A | เข้าใจผิดว่ามี API แล้วรีบอิมพลีเมนต์ทั้งที่ยังไม่มีเซิร์ฟเวอร์รองรับ เสียงานเปล่า |
| A | ออกแบบคีย์ซ้ำซ้อนกับระบบเดิมในอนาคต ต้องรื้อเมื่อ API จริงมา |
| B | ผู้ใช้เข้าใจผิดว่าเบสต์-เอฟเฟิร์ตคือผลค้นจริง ต้องย้ำถ้อยคำไม่รับประกัน |
| B | ไฟล์โลคัลไม่ครบ/ล้าสมัย ทำให้ผลตกหล่น ต้องพึ่งฟอลแบ็กตามลำดับให้ครบ |
สถานะ apply แล้ว — สาขา B อยู่ใน design.md
